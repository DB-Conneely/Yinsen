# Yinsen self-hosted product contract

Locked product reconciliation, 15 October 2026. This document overrides only the listed conflicts and removed scope in the preserved [original product](../legacy/product.md). Retain its other self-hosted behaviours, API envelopes, screens, project state machine and presentation rules. The build is not authorized by this document. Verification priority is functional proof > wired production code > tests/gates; all are required and unproven behaviour is never verified.

## Distribution and supported product

- Ship an MIT-licensed, branded client portal for one freelancer/agency installation. One operator manages clients; clients see only their memberships, invoices and conversations. Primary-client decisions retain their original restrictions.
- Deliver the original public branded page, operator dashboard and client portal. Keep proposals/counters, project lock-in, pause/resume, milestones/approval, versioned deliverables, messaging/attachments, invoices, payment-triggered release, completion/dispute/archive, analytics, settings and session revocation.
- Operator-owned PostgreSQL, local uploads and manual client-link/payment workflows form the zero-provider installation. Optional integrations are direct Stripe, Resend and S3-compatible storage. Each supported option has its own configured proof; it is optional for use of the core product, not exempt from acceptance when advertised as supported.
- Retain the original Next.js/TypeScript/PostgreSQL/Drizzle/custom-session stack and local/S3 storage choice. Use one long-lived application runtime, persisted database/files and in-process SSE/scheduled consumers. Pin supported versions at Phase 1 from current official documentation. Do not add Redis, a job platform, extra workers or a provider framework without a necessary observed requirement and a scoped plan amendment.
- Exclude managed SaaS, `PLATFORM_MODE`, tenant subdomains/RLS hosting, Connect, subscriptions, transaction fees, tier limits/usage metering, platform email, platform admin and inert managed-only schema. Do not prebuild future multi-tenancy. Keep ownership references only where the actual single-installation product consumes them.
- Paid installation/configuration can use the same distribution and operator guide. No product logic, billing system or new user flow is needed for that service. Staff accounts/invitations/RBAC, partial-payment accounting, refunds/tax/accounting automation and imports from the old app are outside this rebuild.
- Docker Compose is the primary installation guide; source development/manual running is documented for contributors. Provider-specific one-click Railway/Render templates are historical options, not additional release targets. Agents rehearse locally with isolated data; Neels performs deployment manually through GitHub CI/CD.

## Identity and invoice numbers

- Exactly one operator account is established through first boot; setup cannot create another operator after completion. Operator and client authentication remain separate flows. An agency is supported as an organisation operated through that account, not as multiple staff logins.
- Trim and consistently normalize client email at creation and login. Uniqueness is installation-wide, including soft-deleted clients; restore the prior client rather than creating a duplicate identity. A separate installation has its own independent database and may use the same email. No cross-installation identity service is needed.
- Session identity and stored project membership determine access. A client-supplied ID never establishes authorization. Project membership does not grant access to another client's invoice or general conversation. Preserve primary/member distinctions and indistinguishable unknown/foreign-resource denial.
- Allocate invoice numbers atomically from the installation's configured prefix/counter. Numbers remain unique and immutable; cancellation/soft deletion never frees them. Prefix/counter edits affect future invoices only and must reject collisions or number reuse. Existing invoices and their URLs remain stable.

These rules replace the old managed/global-uniqueness ambiguity (original Sections 3/4/10). They do not require a multi-tenant schema or cross-instance tests.

## Invoice, checkout and settlement

1. Draft invoices allow editing recipient, items, total override, currency, due date, notes and milestone associations. Sending freezes the financial identity/items/total and release associations; financial changes then require cancel/reissue. Sending issues the portal link and configured email; it does not create Checkout. Failed email sending leaves the invoice draft and visibly retryable, as originally specified. Already-sent invoices cannot be sent as a second issue.
2. Pay is available only to the invoice's client for a sent/overdue payable invoice with configured direct Stripe. Create or reuse one currently usable Checkout Session under a stable idempotency/correlation key. Record immutable invoice identity with each created session and retain correlation after expiry/replacement. A single overwritten latest-session field cannot be the authority for an old payment.
3. Serialize competing Pay, cancel, manual settlement and webhook effects through the invoice's shared writer. Freeze a new checkout while a prior request has an unresolved result; recover its provider result using the same idempotency key before issuing a replacement. Do not blindly create charges after timeouts. Best-effort expire open sessions on cancellation/manual settlement; keep failures visible and retain correlation.
4. Treat paid provider state, amount and currency matching the frozen invoice as the basis for payment acceptance. Browser redirects never prove payment. Verify raw-body signatures using the pinned official Stripe SDK, deduplicate event effects and tolerate out-of-order delivery. If a selected payment method is asynchronous, wire its completion/failure events; an unpaid Checkout completion cannot release files. Unsupported events can be acknowledged; invalid signatures are rejected; a required persistence failure remains retryable rather than acknowledged as successfully processed. A short committed transition is sufficient; no separate queue is prescribed.
5. The first valid sent/overdue -> paid transition records provider payment, releases eligible files, records activity and updates actual UI state. Manual settlement requires the exact full frozen invoice amount, a supported method and reference; lesser/greater amounts are rejected without `settled`, revenue or release. Paid and settled remain terminal money-received states. No partial-payment ledger is added.
6. Repeated receipt of the same payment cannot double-count revenue, issue another domain transition or repeat file release. Expiry/failure cannot reverse successful payment. A late distinct payment for an already paid/settled/cancelled invoice is retained as an operator-visible payment exception with its provider reference; it cannot revive the invoice, double revenue or release files. No automatic refund engine is introduced. The exception has a visible owner action to consult the provider and resolve outside Yinsen.

Native-provider checks informing this reconciliation: [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted) and [webhooks](https://docs.stripe.com/webhooks), read 15 October 2026. Exact SDK/event/version contracts are checked again at the owning task. The serialization, immutable-invoice and exception rules above are Yinsen design decisions, not claims of provider functionality already built.

## File release: preserve the original trigger

An invoice-milestone association is an explicit release trigger. The first full paid/settled transition of **any linked invoice** releases all deliverables/versions then present on its linked milestones. Other linked invoices need not be paid. No association means no automatic release. State this beside invoice associations so the UI does not imply all project money has been collected.

Each new upload/version starts unreleased, including an upload after an earlier payment. The operator may release or relock it manually; a subsequent distinct linked invoice settlement can also release it. A duplicate event on a terminal invoice is a strict no-op and cannot undo a later manual relock. Keep this existing trigger model rather than introducing an all-invoices-paid engine. For a different collection arrangement the operator controls release manually and omits automatic release associations.

Client deliverable/version downloads enforce current identity, project membership and release status on the server, for local and S3 storage. The authorized operator retains download access. Client-visible history cannot grant access to an unreleased older version. Ordinary message attachments require access to their general client or project conversation and have no payment/release gate; public branding assets remain separate. Invoice and milestone associations must belong to the selected project/client relationship; forged cross-project links and file-parent links are rejected. Milestones linked to either paid **or settled** invoices cannot be deleted, reconciling the original paid-only deletion wording with their equal money-received status.

## Product completion boundary

The final accepted product must install from its public instructions with no providers, complete both manual and configured supported-provider journeys, preserve client isolation through all entrypoints, and survive a documented database-plus-files backup/restore rehearsal. Five phases/fourteen tasks define the finite scope; later ideas require a separate request. No dormant SaaS surfaces, fabricated placeholders, unexercised required adapters or old-build completion claims count toward that outcome.
