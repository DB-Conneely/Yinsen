## A21-01 — P1 — Lock-in and milestone approval can confirm terms changed after the client acted

**Classification:** reproduced product correctness defect, not missing proof or an external prerequisite.

**PROBLEM:** The client action records agreement to different terms from those reviewed when the button was clicked. On the current image, the audit created project `5a2ad7d3-eb7c-497d-96d3-abb10340c722` with scope `Original client-visible scope` and budget 12345 GBP minor units. After the real client clicked **Confirm lock-in**, the harness held that ordinary POST at the browser transport. An ordinary operator PATCH committed scope `Changed after client confirmation` and budget 990000. Releasing the unchanged POST returned **200**, persisted `active`, and rendered £9,900.00 under the changed scope. The confirmation had reviewed £123.45. No Yinsen result was mocked; only request arrival order was controlled.

The same root reproduced for the current primary's **Approve milestone**: hold the real approval POST after the click, PATCH the review milestone's name/description to `A21 Unseen approval scope` / `Changed after approval click`, then release. It returns **200** and persists those changed terms as approved. Evidence is the first step of each fresh receipt and executable sequencing in the two scripts. Request bodies are `{}` in the production callers; the harness did not retain an independent body/network trace. Project locks serialize writes, but the checks only compare current status/current primary and cannot know which terms the client reviewed. SSE refresh cannot withdraw a confirmation already sent.

**PROPOSED SOLUTION:** Bind each decision to the relevant server-issued reviewed revision or canonical terms fingerprint, and compare it inside the existing locked transaction before recording the transition. Cover project scope/budget/dates/ordered milestone terms for lock-in and the reviewed milestone content/status for approval. Return a safe conflict and require explicit review again if it changed. A bounded revision/fingerprint in the existing queries/writers is sufficient; no new agreement service is needed. Preserve current role checks, proposal immutable-target semantics and ordinary post-approval operator editing. Include deterministic real-route/browser regressions with the same held-request ordering and unchanged activity/status on rejection. Avoid treating every incoming message as an agreement change merely because it updates `projects.updated_at`.

## A21-02 — P2 — Saving a stale project form silently restores newer fields to their old values

**Classification:** reproduced lost-update defect.

**PROBLEM:** In the actual edit page, the audit changed only the scope input while its displayed project budget was 990000. Another ordinary operator PATCH committed budget 12345 and a new scope. Clicking **Save project** in the still-open edit form returned success and silently restored budget **990000**, despite the operator editing only scope. SQL and the rendered workspace confirmed the restored £9,900.00. `receipt.json` records both budgets; `operate.mjs` retains exact order. ProjectForm always submits every initial field, including members, and `saveProject` overlays them on the locked current record without detecting a stale baseline. Row locking prevents simultaneous physical writes, but cannot preserve the newer values supplied by another tab. The budget loss is reproduced; stale membership restoration is a consequence of the same all-fields payload, not separately claimed as operated proof.

**PROPOSED SOLUTION:** Preserve an edit baseline and prevent stale saves from replacing newer project fields. Reusing a suitable project edit revision from A21-01 for an atomic conflict check is a small coherent option; retain the user's draft and offer current-state review/retry. Sending only genuinely changed PATCH fields additionally preserves unrelated changes, but must still handle two edits to the same field. Keep create behavior and explicit clearing intact. Add a real two-tab/edit-route regression where scope-only saving cannot reset an independently committed budget or membership.

**TOUCHPOINTS:** `src/components/project-form.tsx:35`–`:60` (`submit`, initial field/member state and full edit payload); `src/components/project-views.tsx` (`ProjectEditor`); `src/app/dashboard/projects/[id]/edit/page.tsx`; `src/app/api/projects/[id]/route.ts` (`PATCH`); `src/lib/projects/service.ts:112` (`saveProject` current-field merge and `writeProject`); `src/lib/projects/validation.ts` (`projectPatch`); project query/version contract and `tests/projects.test.ts`/`tests/projects-http.ts`.
