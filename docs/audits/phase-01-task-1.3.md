## Findings

### A13-01 — P1 — Partial updates silently erase saved client information

**PROBLEM:** Authenticated `PATCH /api/clients/:id` with only `{name: "Partial edit renamed"}` returned 200 and permanently cleared existing company, phone, private notes and metadata. PostgreSQL independently confirmed empty strings/`{}`. Installed Zod 4.6.7 applies defaults inside `clientInput.partial()` to omitted properties; spreading parsed data over the locked current row therefore overwrites preserved values. Even an otherwise empty PATCH has this behavior. Existing tests assert the changed subset and miss the erased fields. Evidence: `http-proof.json → defects.partialPatch`, reproduction in `http-proof.mjs`.

**PROPOSED SOLUTION:** Use an update schema that preserves omission without creation defaults, then validate the merged complete record inside the existing transaction. Another small correction is to merge only explicitly supplied validated keys. Keep explicit empty strings/empty metadata available for intentional clearing. Add an installed PATCH regression that checks every untouched persisted field, including `{}` and a metadata-only update.

**TOUCHPOINTS:** `src/lib/clients/service.ts:7` (`clientInput` defaults), `:99` (`saveClient`, especially `:104`/`:115`); `src/app/api/clients/[id]/route.ts:28` (`PATCH`); `src/components/client-forms.tsx:103`; `tests/clients.test.ts` partial-update assertions and `tests/clients-http.ts`. Shared edit root with A13-02: the client writer.

### A13-02 — P2 — Emailed login credentials survive a change of recipient identity

**PROBLEM:** Requested an email login link for client A, changed A's email, then created client B with A's now-free old email. The previously emailed link still returned 200 and authenticated A, revealing A's new current email; it did not authenticate B, whose email now matched the recipient. Tokens store only `client_id`, and editing email neither invalidates pending tokens nor changes their redemption check. This leaves the former address holder with working access after the operator changes the authentication address. Evidence: `http-proof.json → defects.changedRecipient`; all calls used the real email request, PATCH, creation and verification APIs.

**PROPOSED SOLUTION:** On an actual normalized-email change, invalidate pending login tokens in the same existing client-row-locked update transaction. Redemption and edits already share this lock, so the change can serialize without new infrastructure. Also avoid sending a stale address captured before the token-issuance lock: bind the delivery address to the locked current email, or abort if the request's address has changed. Ordinary nonidentity edits must preserve valid links. Verify old-link denial and fresh-link success, including edit/request/redemption races. No assumption about revoking all existing sessions is necessary to fix this pending-token defect.

**TOUCHPOINTS:** `src/lib/clients/service.ts:99` (`saveClient`); `src/lib/auth/client.ts:48`, `:76`, `:119`, `:130` (`issueMagicLink`, `redeemMagicLink`, email lookup/delivery); `magic_link_tokens`; PATCH and native magic-link/verify callers; `tests/clients.test.ts`. Coordinate the same writer owner as A13-01.

### A13-03 — P2 — A later activity failure destroys an already-emailed valid link

**PROBLEM:** A fixture returned a valid native provider acceptance UUID, but a selective real PostgreSQL trigger rejected only `client.email_accepted`. The catch surrounding both send and bookkeeping deleted the newly emailed token, recorded `client.email_failed` and returned 200. Redeeming the captured accepted email's link returned 401. The operator is falsely told delivery failed, and the recipient receives an unusable credential despite successful submission. This is a real owned rollback/error-classification defect, independent of live delivery. Evidence: `http-proof.json → defects.acceptedBookkeeping`; the scoped trigger is retained disabled in the own synthetic database.

**PROPOSED SOLUTION:** Narrow the delivery-failure catch to configuration/template/provider submission. Once submission is accepted, an activity-write failure must not invalidate its token or claim provider failure; log the safe bookkeeping failure separately and preserve accepted truth. Keep genuine failed-send token invalidation. Add the selective accepted-activity-failure regression against real PostgreSQL; blanket database-loss mocks would miss the distinction.

**TOUCHPOINTS:** `src/lib/auth/client.ts:130` (`deliverClientLink`, especially `:148`–`:151`); `src/lib/clients/service.ts:57` (`recordActivity`); native request caller; operator activity labels in `src/app/dashboard/clients/[id]/page.tsx`; `tests/clients.test.ts`. Same auth/email root owner as A13-04/A13-05.

### A13-05 — P2 — Synchronous delivery reveals account existence through response timing

Only an existing active client enters the awaited network delivery path, making the claimed non-enumeration property false during slow/rejected provider operation; ordinary provider latency also distinguishes the branches. Throttling limits attempts but does not remove this signal. Evidence: `http-proof.json → defects.emailTiming`; real native HTTP and SQL, only the unavailable provider boundary controlled.

**PROPOSED SOLUTION:** Give both lookup outcomes the same bounded outward completion policy. For the current finite synchronous design, a shared response deadline covering the existing provider timeout, applied from before the identity lookup, is a small option; review its resource/latency tradeoff and ensure failures/early rejections follow it too. A different minimal strategy must demonstrate that provider latency is not exposed only for existing addresses. Coordinate the public failure decision in A13-04 without returning client-specific delivery status. Add an actual HTTP timing regression with a controlled slow external boundary and comparison addresses, not merely equal-envelope assertions.

**TOUCHPOINTS:** `src/lib/auth/client.ts:119`–`:126`; `src/lib/email/resend.ts:6` timeout boundary; `src/pages/api/auth/magic-link.ts`; existing generic-known/unknown tests and external-fetch proof. Shared request/delivery root with A13-03/A13-04; one edit owner should integrate them.
