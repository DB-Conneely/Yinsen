## Findings

### A12-01 — Medium / P2 — Email failure overwrites the verified database state and traps first boot

**PROBLEM:** On the actual wizard, a native `/api/setup/verify` HTTP 200 response contained `{ database: "configured", email: "failed", payments: "skipped", storage: "skipped" }`. `useWizard.verify()` then threw on the email outcome, caught it as a database failure and displayed **Database: Failed**. Continue displayed “Verify the installation before continuing” and stayed at step 2. There is no optional-email skip/manual choice. The database was demonstrably healthy; changing only the external provider response to acceptance immediately allowed the unchanged database/account to complete setup.

The false database label is a definite state/coherence defect. Blocking on configured-but-rejected optional email is its additional visible flow consequence: retained setup detail supplies verify/skip, and the active contract preserves providerless/manual use while moving secrets to the server environment. This differs from startup correctly refusing _partially supplied_ configuration. The complete, syntactically valid fixture configuration passed startup; only provider verification failed. An operator could remove email configuration and restart, but the wizard supplies no direct manual continuation and misleadingly directs attention to the required database check.

**PROPOSED SOLUTION:** Keep the required database result independent from optional email outcome. Preserve the verified database state and visible email failure, and honor the optional/manual path with a deliberate skip/continue choice rather than fabricating provider acceptance. A focused installed regression should return this real mixed result and check truthful per-service status and the intended continuation/retry behavior. The fresh patcher should assess the configured-provider blocking policy against the retained verify/skip contract; the certain database mislabel needs correction either way.

**TOUCHPOINTS:** `src/components/setup-wizard.tsx:222` (`useWizard.verify`, email failure branch at 254, catch at 261), step-2 gate at 286, `Integrations` rendering and completion summary; `src/pages/api/setup/verify.ts:13` (`verifySetup`, authoritative independent results); `src/lib/email/resend.ts:46` (`verifyEmail`); actual `/setup` browser regression. No database migration, provider credential editor or generic integration framework is suggested. Shared email sender semantics remain Task 1.3's root.

**EVIDENCE:** `.local/audit-12/browser-proof.json` records the native response, exact displayed text and blocked step; `wizard-email-failure.png` shows the outcome. `external-boundary.jsonl` binds only the replaced provider boundary. `browser.mjs` reproduces failure then recovery through installed owned code.

### A12-03 — Medium / P2 — A failed proxy renewal bypasses normal safe page failure handling and headers

**PROBLEM:** With a real valid operator cookie, scoped `REVOKE UPDATE ON operator_sessions FROM yinsen_runtime` in the isolated database made the dashboard request fail inside the proxy's sliding-session renewal. The installed response was bare HTTP 500 **“Internal Server Error.”**, with no retry control and none of the configured `X-Frame-Options`, `X-Content-Type-Options`, CSP, Referrer-Policy or Permissions-Policy headers. `/api/auth/me` under the same denial returned 503 through its owned safe boundary. Restoring the grant and reloading recovered the same session. A database outage/renewal-query failure can reach the same uncaught await; this is not merely a bad-cookie denial.

This is narrower than the global-shell concern: actual settings-query failures did show the current framework's safe Reload UI. The uncaught proxy await fails before that page boundary and before a normal response can retain the header contract. No unauthorized data release or credential disclosure was observed.

**PROPOSED SOLUTION:** Handle a supplementary renewal failure explicitly, without issuing a renewed cookie or weakening page/API authorization. The smallest candidate is to safely log the failure and let the existing independently authorized page caller produce its normal safe error/recovery outcome; retain immediate expired/revoked denial and actual sliding renewal on success. Add an installed failure regression covering safe visible recovery and configured headers, then restore the DB capability and confirm the original session works. Avoid another authentication framework.

**TOUCHPOINTS:** `src/proxy.ts:8` (`proxy`, uncaught `validateOperatorSession` await at 13); `src/lib/auth/session.ts:31` (sliding UPDATE failure); actual dashboard and portal matcher callers; `src/lib/auth/page.ts:9` and protected layouts (independent authorization must remain); existing safe logging and response-header contract in `next.config.ts:9`. Cross-reference **A11-01** in the [Task 1.1 report](phase-01-task-1.1.md): that finding owns the separate HSTS/global configuration correction. This finding owns the proxy failure root; it does not propose a competing edit to `next.config.ts`.

**EVIDENCE:** `.local/audit-12/failure-proof.json` → `proxy` records the real 500, full safe response-header names/values, empty button list and comparison API status; `proxyRecovered` proves recovery. `failures.mjs` targets only the new synthetic database and restores both changed grants in `finally`.
